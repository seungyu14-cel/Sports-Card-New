# 로컬 LLM + Feedback Memory 운영 가이드

## 실행

OpenAI API Key 없이 다음 흐름으로 동작합니다.

MD 파일 → Ollama → 직원별 역할 프롬프트 → 10페이지 카드뉴스 → 직원별 피드백 → SQLite Feedback Memory → 다음 제작에 재사용

권장 명령:

    ollama serve
    ollama pull qwen3:8b

.env:

    OLLAMA_BASE_URL=http://127.0.0.1:11434
    OLLAMA_MODEL=qwen3:8b

웹 실행:

    python -m pip install -e ".[dev]"
    sports-card-news-web --open-browser

로컬 전용 화면:

    http://127.0.0.1:8787/local

## Feedback Memory 원칙

좋은 규칙 예시:

- 표지에서 승패를 반복하지 말고 결정적 사건을 첫 15자 안에 배치한다.
- 숫자는 MD 원문에 존재하는 값만 사용하고 단위를 원문과 동일하게 유지한다.
- TOP 이슈는 서로 다른 사건으로 구성하고 같은 장면을 표현만 바꿔 중복시키지 않는다.

저장하면 안 되는 내용:

- 특정 경기의 스코어
- 특정 선수의 당일 기록
- 특정 날짜의 부상 상태

이런 내용은 사실 데이터이지 다음 제작에 재사용할 편집 규칙이 아닙니다.

분할 제작에서는 직원별 최신 learning_rule 1개를 해당 직원의 검수에 적용하고, 편집국장의 최신 규칙은 카드 작성에도 적용합니다.

## 23명 직원 교육 프로필 적용 방식

고정 교육 과정은 `src/sports_card_news/employee_training.py`에 저장됩니다.

각 직원은 다음 6개 필드를 가집니다.

- `focus`: 집중 학습 분야
- `core_rule`: 가장 중요한 단일 개선 규칙
- `study_topics`: 반복 학습할 세부 주제
- `decision_rules`: 실제 판단 순서
- `checklist`: 결과 검수 체크리스트
- `forbidden`: 절대 하면 안 되는 행동

로컬 제작 시에는 선택한 리그에서 근무하는 직원별로 요청을 나눠, 지정된 카드와 근거를 검수할 때 해당 교육 프로필을 주입합니다. 카드 작성에는 공통 핵심 규칙을 적용합니다.

예:

    KBO
    → 공통 편집/검증/콘텐츠/SNS 직원
    → 정유진 야구 데스크
    → 김태훈 KBO 기자

    NPB
    → 공통 편집/검증/콘텐츠/SNS 직원
    → 정유진 야구 데스크
    → 이현석 NPB 기자

    MLB
    → 공통 편집/검증/콘텐츠/SNS 직원
    → 정유진 야구 데스크
    → 정민우 MLB 기자

## 고정 교육 + Feedback Memory 우선순위

학습 규칙은 다음 우선순위로 적용합니다.

1. MD 원문 사실
2. 직원별 고정 교육 프로필
3. 사용자가 입력한 추가 편집 지시
4. 최근 Feedback Memory

Feedback Memory가 고정 교육과 충돌하면 고정 교육을 우선합니다.

예를 들어 과거 피드백에 특정 선수나 특정 경기 스코어가 들어가더라도 다음 경기 사실로 재사용하지 않습니다.

## 학습 데이터 작성 원칙

좋은 학습 데이터는 다음 형식입니다.

    입력 상황
    → 잘못된 결과
    → 왜 잘못됐는지
    → 올바른 결과
    → 다음부터 적용할 일반 규칙

예:

    입력: MD에는 8K
    잘못된 결과: 카드에 9K
    이유: 숫자 원문 불일치
    올바른 결과: 8K
    학습 규칙: 탈삼진 숫자는 MD 원문과 1:1 대조한다.

반대로 다음처럼 특정 경기 사실만 저장하는 것은 피합니다.

    김도영은 42호 홈런을 쳤다.
    KT는 9-0으로 이겼다.

이런 내용은 다음 경기에서 재사용할 수 없는 사실 데이터입니다.

## UI

### MD 원문 번호 선택과 진단 기록

- 모든 리그의 MD 분석은 프로그램이 만든 원문 구절 번호(예: `C001-S002`)를 AI가 선택하는 방식입니다. AI는 번호와 중요도만 반환하고, 근거 문장은 프로그램이 원문에서 가져옵니다. `라얀`을 `라yan`으로 다시 쓰는 오류가 근거에 들어가지 않습니다.
- 강조·인라인 코드·제목·목록 표시와 연속 공백/줄바꿈만 정리합니다. 선수명, 숫자, 점수 하이픈, 소수점은 바꾸지 않습니다. 문장/문단 경계를 우선하며 160자를 넘는 구절은 공백 위치를 우선해 나눕니다. 구절 번호는 해당 MD 구간에서만 유효합니다.
- 번호 목록이 길면 작은 요청으로 나누어 모두 전달하고, MD 구간당 중요도 상위 근거 최대 4개를 다음 단계에 넘깁니다. 5자 미만의 단독 구절은 선택 후보에서 제외됩니다. 원문 전체는 기록에 보존됩니다.
- Ollama 요청의 `format`에 JSON Schema를 전달합니다. 단순 `format: "json"`은 필드·자료형·번호까지 제한하지 못하므로, 이번 요청에 실제로 있는 번호를 `enum`으로 지정하고 `source_id`·정수 `importance`를 필수로 제한합니다. 카드·캡션·사실 관계 판정·직원 검수에도 해당 응답 스키마를 적용합니다. [Ollama 공식 구조화 출력 안내](https://docs.ollama.com/capabilities/structured-outputs)를 따르며 로컬 Ollama가 필요합니다.
- 유효한 동일 번호의 중복 선택은 한 번만 반영하고 높은 중요도를 사용합니다. 다른 문장으로 대체하지 않으며 `normalizations`에 정리 내역을 남깁니다. 없는 번호, 다른 구간/요청의 번호, 잘못된 필드·자료형·JSON은 해당 요청만 한 번 재시도합니다. 두 번 모두 실패하면 `검토 대기`로 중단하고 화면에 구체적인 오류 필드와 진단 기록 링크를 표시합니다. 통신 오류·출력 한도 초과는 자동 재시도하거나 근거를 임의 생성하지 않습니다.
- 각 실행 폴더 `output/studio/local-.../`의 `extraction-diagnostic-001.json`은 schema_version 3입니다. `response_format`, 모델명, `source_chunk`, `normalized_source`, 구절 번호/문장/위치 목록인 `source_units`, 실제 AI 응답/오류인 `attempts`, 최종 선택 문장인 `selected_quotes`를 저장합니다. 성공·재시도·모델 통신 실패에도 기록을 남깁니다. 형식 제약과 별도로 원문 번호 소속 검증 및 이후의 KBO 사실 관계 검수는 유지합니다.
- 완성 ZIP에도 추출 진단 JSON이 포함됩니다. 이 파일에는 업로드한 원문이 있으므로 공유할 때 확인하세요. 이전 버전 기록의 `model_quotes`·`rejected_quotes`는 기존 기록에서만 사용합니다.
- 이 단계는 업로드한 원문 보존을 검증합니다. 원문 자체의 공식 사실 여부나 생성된 카드의 표현 정확성과는 별개입니다. KBO의 카드별 검수·수정은 다음 단계에서 그대로 실행됩니다.

수정판 실행: 실행 중인 서버 창에서 `Ctrl+C`로 중지 → 프로젝트 폴더에서 `git switch main`, `git pull --ff-only origin main`, `.\start.bat` → 브라우저 새로고침 후 MD 재업로드. EPL 자료라면 카테고리도 EPL을 선택하세요. 이전 실패 작업은 재개되지 않으므로 새로 제작을 시작해야 합니다.

10%에서 `원문 번호 선택` 오류가 나면 MD 업로드 이후 AI 응답 형식 검증에서 멈춘 것입니다. MD가 손상되었다는 뜻은 아닙니다. `facts.0.importance: 필수 필드 누락`처럼 화면에 표시된 구체적인 원인을 확인하세요. 같은 문제가 반복되면 **그 실행의** 진단 JSON과 원본 MD를 함께 확인해야 합니다. 이전 실행의 JSON이나 화면만으로 실제 AI 응답을 확정할 수 없습니다. Ollama가 스키마 요청에 HTTP 오류를 반환하면 서버 오류 문구를 확인하고 로컬 Ollama를 업데이트하세요. 구버전 방식으로 조용히 우회하지 않습니다.

`/local` 화면의 직원 카드에서 다음을 확인할 수 있습니다.

- 근무 중 / 오늘 미배정
- 팀과 직책
- 집중 학습 분야
- 핵심 교육 규칙

따라서 이 화면을 직원 학습 현황을 확인하는 운영 공간으로 사용할 수 있습니다.
